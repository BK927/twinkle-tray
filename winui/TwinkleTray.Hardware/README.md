# Windows monitor backend

`MonitorService` uses Windows' physical monitor APIs (`Dxva2.dll`) for DDC/CI, `System.Management` for built-in display brightness, DisplayConfig/DXGI for HDR, GDI for software dimming, and native HID feature reports for Apple Studio Displays. All monitor refreshes and writes are serialized and run away from the UI thread.

- Call `RefreshAsync()` before writing, and again after hotplug, resume, or display configuration changes. A refresh creates a replacement handle set, reads brightness/contrast, and disposes the old handles after the replacement succeeds. A failed or canceled refresh disposes its incomplete replacement.
- Check the snapshot's support flags before enabling a slider. Unsupported displays are retained. `Brightness` and `SupportsBrightness` always describe hardware brightness; gamma never replaces these values. `SdrBrightness`, `GammaBrightness`, and `SupportsGammaBrightness` describe the separate software controls. `LastRefreshErrors` reports nonfatal provider failures without preventing working displays from appearing.
- Monitor IDs combine the normalized display device interface ID with its physical index. WMI IDs are normalized to the same device identity, so built-in panels are not also shown as unsupported DDC devices. Windows may change the instance ID when a display is moved to a different physical port.
- Brightness and contrast use VCP `0x10` and `0x12`, with their actual monitor maximum. High-level Windows brightness/contrast APIs are a fallback when the driver advertises them. The upstream `FUS087C`/`FUS06AB` brightness overrides are retained; `HardwareOptions.BrightnessCodes` can override a snapshot ID, device instance ID, or model ID. WMI snaps to an advertised supported brightness level.
- `GetFeaturesAsync()` explicitly reads and parses the capabilities string, then reads advertised brightness, contrast, volume, mute, input, color gain/preset/temperature, power, and configured custom VCP codes. `GetVcpAsync()` reads one requested code, including custom codes omitted from those capabilities. Neither writes values. `BrightnessVcp` reports the snapshot's detected brightness code. `SetVcpAsync()` first requires a successful read and enforces known continuous ranges and advertised discrete choices. `PowerOffAsync()` requests VCP `0xD6 = 5`; firmware support/wake behavior varies. Use `SetVcpAsync()` for a different advertised power value.
- HDR uses modern DisplayConfig color information with a read-only DXGI fallback to distinguish HDR from SDR with automatic color management. `SetSdrBrightnessAsync()` uses the same private Windows SDR-white-level setter as upstream: percentages map to 80–480 nits. `ForceHdrDisplays` permits the getter/setter on explicitly chosen targets without falsifying detected `HdrActive`.
- `SetGammaBrightnessAsync()` applies the upstream monotonic dimming curve with its 20% floor, preserves the exact ramp present before its first write, verifies the result, and checks that a hotplug has not reassigned the GDI output to another display. `GammaDisplays` identifies all per-monitor gamma owners for restoration when they are removed. `EnableGamma`/`SoftwareFallback` request read-only gamma observations. The application chooses its main slider's control route explicitly.
- `RestoreGammaAsync()` and `Dispose()` restore only ramps this service wrote. They avoid overwriting a later external calibration change or a different physical display. No ramp writes occur when this instance only read displays. Configure restores removed gamma routes asynchronously; refresh after changing control providers or brightness codes to rebuild available controls.
- Apple Studio Display brightness uses report 1 on HID interface `MI_07`, VID `05AC`, PIDs `1114`, `1116`, and `1118`, with the same 400–60000 scale as upstream. Serial matching avoids ambiguous associations when multiple displays are connected. No USB driver is installed or replaced. Devices whose current driver exposes only libusb/WinUSB rather than the Windows HID interface require an appropriate existing HID interface; detection reports that limitation.
- `AmbientLightService` reads the Windows default or a selected sensor device ID and Yoctopuce hub light-sensor readings. `GetDevicesAsync()` lists valid selector IDs; Yoctopuce accepts either a serial or `serial.function` selector. `DesktopEnvironment` observes foreground app paths, fullscreen state, media playback, idle time, and session-lock state.
- Cancellation is cooperative between driver calls. Windows does not offer an interruption mechanism for an in-progress DDC/CI call. `VcpReadDelayMilliseconds` adds a cancellation-aware worker delay (0–2000 ms) before reads for hardware that needs it. Live hardware writes, WMI laptop brightness, Apple displays, real sensors, and hotplug/restore behavior still require target-hardware validation.

Build the library:

```powershell
dotnet build winui/TwinkleTray.Hardware/TwinkleTray.Hardware.csproj
```

Run the explicitly read-only diagnostic:

```powershell
dotnet run --project winui/TwinkleTray.Hardware/Diagnostics/TwinkleTray.Hardware.Probe.csproj -- --read-only
```

The diagnostic validates ID normalization, native structure sizes, VCP capabilities parsing, gamma curve invariants, two real monitor refreshes, snapshot ranges/unique IDs, argument validation, cancellation, and repeated disposal. Add `--features` to read live capabilities and feature values. It never sends valid arguments to any hardware write operation. On the development system it read two monitors, HDR capability/mode, gamma, brightness/contrast, input, volume, power and color controls successfully.
